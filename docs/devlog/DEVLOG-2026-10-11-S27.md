### What Was Built
**The plan says where each tool is installed.** A plan step written by autoplan on kind:

```yaml
- name: external-secrets
  currentVersion: v0.10.5
  targetVersion: 2.11.0
  risk: LOW
  source: fluxcd
  namespace: external-secrets
  releaseName: external-secrets-external-secrets
  chart: {name: external-secrets, version: 2.11.0, repository: "https://charts.external-secrets.io/"}
  managedBy: {kind: HelmRelease, namespace: flux-system, name: external-secrets}
```

- `chart.version` is the KB's `chart_version` for the target. It differs from the app version for
  prometheus-stack (0.94.0 → chart 91.0.0) and vault (2.0.4 → 0.34.1).
- `chart.repository`: the one the install records (an Argo CD Application's `repoURL`, a Flux
  HelmRepository's `url`), otherwise the KB's. A plain Helm release does not record where its chart came
  from.
- A raw install has no release and no chart; `managedBy` is set for the fluxcd and argocd sources.
- `planStep` skips a target the KB has no chart version for (logged).

**Chart repositories in the knowledge base.** New tool-level field `chart_repository`
(https:// or oci://), required when the versions have chart versions. The six values are the indexes S26
verified against. Istio uses `https://blob.istio.io/istio-release/charts`, which serves every base and
istiod chart in the KB; the old GCS index stops at 1.30. A Go script fetched each live index and found
all 128 chart versions (114 entries plus istiod for each Istio entry) with the KB's app version.

**Scanners.** `InstalledTool.ManagedBy` names the Flux HelmRelease or Argo CD Application. For Flux, the
HelmRepositories are listed once per scan (v1, then v1beta2). The `url` of the one a HelmRelease names
becomes `RepoURL` and chart-origin evidence. A list the operator may not make costs only the urls.

**Approval in spec.**
- `spec.approved` (CRD default `false`) lets the operator carry out a plan.
- A CRD rule (`!has(oldSelf.approved) || !oldSelf.approved || self == oldSelf`, "an approved plan
  cannot change") makes the approved plan the one that runs. Approval cannot be withdrawn; delete the
  plan instead.
- Autoplan's `autoApprove` sets `approved: true` at create. The S25 race (finding 9) is gone with the
  status update after create.
- The UI server's approve endpoint patches `spec.approved`; approving twice is a no-op.

**StackUpgrade reconciler.**
- A plan waiting for approval is not requeued. The approval is a spec change, which the watch delivers;
  on kind the approved plan was Upgrading in the same second.
- No `Requeue: true`. Phase changes return `RequeueAfter: stepInterval` (5s); the watch event of the
  status write usually comes first.
- **Bug fixed: finished plans ran again.** The old `default` branch caught Succeeded and RolledBack and
  reset them to Pending. A plan created without `approvalRequired` (autoApprove) would then run again on
  its next reconcile, including the one its own status write triggered. With approval in spec every
  approved plan would have looped. Final phases now end.
- **Stale-copy guard.** Before a step runs, its `Progressing`/`StepStarted` condition is written with
  the plan's resourceVersion. A copy read from a cache that lags behind the write that finished the
  previous step fails with a conflict and is retried after `stepInterval`, instead of running that step
  again. The race came from requeues firing while a long Helm step ran.
- **The executor gets the install.** Before, it got the tool name as release and chart, the app version
  as chart version and no namespace (audit #1). `helmStep` passes the release, namespace, chart name,
  repository URL (an `oci://` repository becomes the full chart reference) and the chart version.
- The Ready condition reads `WaitingForApproval`, then `Approved`, then `Upgrading`.

### Key Decisions
1. **The plan records the install, not just the tool.** Autoplan writes what the scan saw (source,
   namespace, release, managing object) at plan time. The executor (S29) and PR generation (S42–44) act
   on the plan rather than re-scanning, and the approver sees exactly which release and chart will be
   touched.
2. **The chart repository: the install's, else the KB's.** Argo CD and Flux record theirs; plain Helm
   does not, so the KB gained `chart_repository`. The approver can see the value in the plan. A mirror or
   air-gapped repository needs an override (todo).
3. **`spec.approved`, not `approvalRequired`.** Every plan needs an explicit approval; autoApprove sets
   it. One field, one write, no race with the StackUpgrade controller.
4. **An approved plan cannot change (CRD rule).** Approval in spec would otherwise let anyone edit the
   target after approving. The rule also forbids withdrawing the approval: once approved, the operator
   starts at once, so a withdrawal would mean nothing. Deleting the plan is the way out.
5. **No polling for approval; `RequeueAfter` after phase changes.** The status write's watch event drives
   the next phase; the requeue is a fallback. The stale-copy guard makes that fallback safe during long
   Helm steps.
6. **Helm write RBAC is not granted here.** The kind check showed a Helm upgrade needs create/update on
   release Secrets and on every kind a chart renders. A broad ClusterRole versus impersonating a per-plan
   ServiceAccount (as Flux's `serviceAccountName` does) is a security decision; it goes to S29.
7. **`ToVersion` stays the chart version** in `planner.UpgradeStep` (the executor always used it so);
   the comments now say so instead of renaming fields the S29 router will rework.

**Spec дэх approval.**

  change") approve хийсэн төлөвлөгөө л ажиллахыг баталгаажуулна. Approval-ийг буцааж болохгүй;
  оронд нь төлөвлөгөөг устгана.
- Autoplan-ий `autoApprove` create үед `approved: true`-г тавина. Create-ийн дараах status update-тэй
  хамт S25-ийн race (9-р дүгнэлт) алга болсон.
- UI серверийн approve endpoint `spec.approved`-ийг patch хийнэ; хоёр удаа approve хийх нь no-op.

**StackUpgrade reconciler.**
- Approval хүлээж буй төлөвлөгөөг requeue хийхгүй. Approval бол spec-ийн өөрчлөлт бөгөөд watch түүнийг
  хүргэнэ; kind дээр approve хийсэн төлөвлөгөө тэр секундэд Upgrading болсон.
- `Requeue: true` байхгүй. Phase-ийн өөрчлөлт `RequeueAfter: stepInterval` (5s) буцаана; status
  бичилтийн watch event ихэвчлэн түрүүлж ирнэ.
- **Засагдсан алдаа: дууссан төлөвлөгөө дахин ажилладаг байсан.** Хуучин `default` салбар Succeeded,
  RolledBack-ийг барьж, Pending болгон буцаадаг байв. `approvalRequired`-гүй (autoApprove) үүссэн
  төлөвлөгөө дараагийн reconcile дээрээ, тэр дундаа өөрийнхөө status бичилтийн өдөөсөнд, дахин ажилладаг
  байв. Spec дэх approval-тай бол approve хийсэн төлөвлөгөө бүр давталтад орох байсан. Эцсийн phase-ууд
  одоо зогсоно.
- **Хуучирсан хуулбарын хамгаалалт.** Алхам ажиллахаас өмнө түүний `Progressing`/`StepStarted`
  condition төлөвлөгөөний resourceVersion-тэй бичигдэнэ. Өмнөх алхмыг дуусгасан бичилтээс хоцорсон
  cache-ээс уншсан хуулбар conflict-оор унаж, тэр алхмыг дахин ажиллуулахын оронд `stepInterval`-ийн дараа
  дахин оролдоно. Race нь урт Helm алхмын үеэр requeue өдөөгдсөнөөс үүсдэг байв.
- **Executor суулгалтыг авна.** Өмнө нь хэрэгслийн нэрийг release ба chart болгон, app хувилбарыг chart
  хувилбар болгон авч, namespace авдаггүй байв (аудит #1). `helmStep` release, namespace, chart-ийн нэр,
  repository URL (`oci://` repository бүтэн chart лавлагаа болно), chart хувилбарыг дамжуулна.
- Ready condition `WaitingForApproval`, `Approved`, `Upgrading` гэж дараалан уншигдана.
